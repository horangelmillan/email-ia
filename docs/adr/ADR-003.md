# ADR-003: Puertos y errores de dominio en `packages/core`; adaptadores fuera del núcleo

- **Estado**: Aceptado
- **Fecha**: 2026-08-20
- **Reemplaza a**: Ninguno (refina ADR-002, IA/LLM)
- **Referencias**: ARCHITECTURE_DECISIONS.md §3.6-3.7 y §8 (D4, D5), ADR-002, PROJECT.md, ENGINEERING.md

## Contexto

Durante el spike de Fase 1, `AIProviderPort`, sus tipos (`ChatMessage`, `ChatOptions`, `ChatResponse`, `EmbeddingResult`, `ModelInfo`, `AIProviderConfig`) y `ProviderError` nacieron dentro de `packages/ai-provider`, junto al adaptador `OpenAICompatibleProvider`. El proyecto define `packages/core` como "Shared Kernel + Domain (núcleo hexagonal)" y `packages/ai-provider` como paquete de proveedores de IA (ADR-002 §IA). En arquitectura hexagonal, el **puerto** (contrato) pertenece al núcleo y los **adaptadores** lo implementan: si el contrato vive en el paquete del adaptador, el dominio quedaría acoplado a una infraestructura concreta y cualquier otro consumidor (backend, servicios de aplicación futuros) tendría que depender de `ai-provider` para conocer el contrato.

## Decisión

- `AIProviderPort` y sus tipos pasan a `packages/core/src/ports/ai-provider.port.ts` y se re-exportan desde `packages/core`.
- `ProviderError` pasa a `packages/core/src/errors/provider-error.ts`, extendiendo el error base unificado `AppError` (`packages/core/src/errors/app-error.ts`), que implementa la estrategia unificada de excepciones (ENGINEERING: AppError + códigos; ARCHITECTURE_DECISIONS §3.5) con `code`, `status` y `details` opcionales.
- `packages/ai-provider` queda como **adaptador** del puerto: implementa `AIProviderPort`, lanza `ProviderError` (del Core) y re-exporta el contrato y el error para mantener su API pública (los consumidores existentes, p. ej. `packages/backend`, no cambian sus imports).
- Dependencia de `@email-ia/shared` en `ai-provider` eliminada (no se usaba) y sustituida por `@email-ia/core`.

## Alternativas evaluadas

| Opción                                           | Resultado                                                              |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| Contrato en `packages/core` (puerto) + adaptador | **Elegida**: hexagonal clásico, dominio desacoplado de infraestructura |
| Mantener contrato en `packages/ai-provider`      | Descartada: acopla el dominio al paquete de un adaptador concreto      |
| Puerto en `packages/shared`                      | Descartada: `shared` es para tipos/utilidades genéricas sin semántica  |
| Paquete `domain` separado                        | Descartada: YAGNI; `core` ya es el núcleo del hexágono                 |

## Consecuencias

**Positivas**

- `packages/core` deja de ser un placeholder y materializa el contrato del hexágono (puertos + errores de dominio).
- Cualquier consumidor (backend, servicios de aplicación futuros, Web) depende solo del Core para el contrato de IA.
- `AppError` establece la base unificada para el resto de errores de la aplicación (mapeo HTTP en Fase 2+).

**Negativas / pendientes**

- `ai-provider` ahora depende de `@email-ia/core` (topológico: core debe compilarse antes).
- Re-export del contrato desde `ai-provider` es conveniencia de compatibilidad; los nuevos consumidores deben importar desde `@email-ia/core`.
- El mapeo HTTP de `AppError` y el resto de puertos del dominio (correo, persistencia) quedan pendientes de Fase 2.
