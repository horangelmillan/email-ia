# ADR-005: Runtime IA embebido (llamafile) + adaptadores Ollama/LM Studio + gestor de modelos

- **Estado**: Aceptado
- **Fecha**: 2026-08-20
- **Reemplaza a**: Ninguno (concreta ADR-002 §IA/LLM y ARCHITECTURE_DECISIONS §3.7; refina ADR-003)
- **Referencias**: ARCHITECTURE_DECISIONS §3.7, ADR-002, ADR-003, PROJECT_STATE Fase 2 Tarea 3, spike 2026-08-19

## Contexto

Fase 2 requiere materializar el runtime embebido y los adaptadores multi-proveedor sin acoplar el dominio a una infraestructura concreta. El spike (2026-08-19) validó: `node-llama-cpp` exige bindings nativos solo en main de Electron; `llamafile` es binario único portable con servidor OpenAI-compatible sin instalación; `Ollama` (`http://localhost:11434/v1`) y `LM Studio` (`http://localhost:1234/v1`) exponen la misma API (`/v1/chat/completions`, `/embeddings`, `/models`). `AIProviderPort` ya vive en `packages/core` y `OpenAICompatibleProvider` en `packages/ai-provider` cubre chat/embed/listModels pero deja `pullModel` no soportado (ADR-003). Falta gestión de modelos independiente del runtime (download/version/quantization §3.7) y ciclo de vida del binario embebido.

## Decisión

- **Puerto en Core**: nuevo `ModelManagerPort` (`packages/core/src/ports/model-manager.port.ts`) con `listLocalModels()`, `pullModel(name, onProgress?)`, `removeModel(name)`, `getModelPath(name)` y tipos `LocalModelInfo`/`PullProgress`. `AIProviderPort.pullModel` se mantiene como fachada del dominio; `ModelManagerPort` es la capacidad de gestión desacoplada del runtime (hexagonal: puerto en Core, adaptador en `ai-provider` / `db` según implementación).
- **Driver IA**: `OpenAICompatibleProvider` permanece genérico (timeout 30s, normaliza `baseUrl` añadiendo `/v1`, DI de `fetch`). `OllamaProvider` extiende la semántica y mapea `pullModel` a `POST {base}/api/pull` (Ollama fuera de `/v1`) con streaming NDJSON opcional y `ProviderError` unificado. `LM Studio` y OpenAI se sirven con `OpenAICompatibleProvider` (pull no soportado, error explícito).
- **Runtime embebido**: `LlamafileRuntime` (`packages/ai-provider/src/llamafile-runtime.ts`) gestiona el binario único: `binaryPath` + `modelPath` + `port/host/args`, valida binario vía `fs.existsSync` inyectable, `spawn` inyectable, `getServerUrl()` (`http://host:port/v1`), `isRunning()`, `healthCheck()` (`GET /v1/models`), `start()`/`stop()`. `LlamafileProvider` delega `chat/embed/listModels` a `OpenAICompatibleProvider` apuntando al servidor del runtime y expone `ensureRunning()` + `pullModel` vía `LocalModelManager`.
- **Gestor local**: `LocalModelManager` (`filesystem-model-manager.ts`) implementa `ModelManagerPort` sobre filesystem: directorio base configurable, `fetch` inyectable para descarga, `fs` inyectable para tests (sin red/disco real), detección de cuantizaciones por nombre de fichero.
- **Factory**: `createAIProvider(config, deps?)` soporta `config.provider = 'openai-compatible' | 'ollama' | 'lmstudio' | 'llamafile'` (default `openai-compatible`) con `baseUrl` por defecto (`ollama: http://localhost:11434`, `lmstudio: http://localhost:1234`, `llamafile: http://localhost:8080`) y normalización `/v1`. Para `llamafile` se inyecta `LlamafileRuntime`. Re-exporta `ModelManagerPort` desde `@email-ia/core`.
- **Hexagonal**: `packages/core` sin dependencia de `ai-provider`; `packages/ai-provider` depende de `@email-ia/core` y adapta ambos puertos. Orden: `core → ai-provider → backend/electron`.

## Alternativas evaluadas

| Opción                                                      | Resultado                                                                                     |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `pullModel` solo en `AIProviderPort` sin `ModelManagerPort` | Descartada: mezcla capacidad de gestión con inferencia; impide gestor independiente §3.7      |
| `node-llama-cpp` embebido directo                           | Descartada: requiere bindings nativos en main + build from source, no portable (spike)        |
| `Transformers.js` WASM en renderer                          | Descartada: más lento, memoria limitada, sin soporte modelos GGUF grandes                     |
| `better-sqlite3` nativo para registro de modelos            | Descartado YAGNI Fase 2; filesystem JSON suficiente, evoluciona a DB cuando haya vector store |

## Consecuencias

Positivas:

- Binario único portable sin instalación del usuario; fallback transparente a Ollama/LM Studio/OpenAI vía misma `AIProviderPort`.
- `pullModel` funciona en Ollama y local filesystem; OpenAI-compatible falla con `ProviderError` explícito (no regresión de tests existentes).
- Tests sin red/disco nativo (DI de `fetch`/`fs`/`spawn`), cobertura ≥80 %.

Negativas / pendientes:

- `LlamafileRuntime.start()` requiere binario real para E2E; en CI solo se valida healthCheck mockeado.
- RAG/embedding chunking, prompts versionados y vector store quedan para Fase 2+ (esquema `emails` ya preparado).
- Cuantización auto-recomendada por hardware queda como `suggestQuantization()` pendiente de implementación.
