# ADR-002: Stack técnico core (backend, frontend, persistencia, IA, desktop, observabilidad)

- **Estado**: Aceptado
- **Fecha**: 2026-08-19
- **Reemplaza a**: Ninguno
- **Referencias**: ARCHITECTURE_DECISIONS.md §3.5-3.7 y §8 (D4-D10), PROJECT.md, ENGINEERING.md

## Contexto

El proyecto requiere un stack completo y desacoplado para una app de gestión de correos con IA local: backend reutilizable para Web, frontend SAPUI5, persistencia local cifrada, IA con múltiples runtimes posibles y contenedor Electron. Cada elección debía validarse con las mejores prácticas actuales (2026) y respetar la filosofía privacy-first y Desktop First.

## Decisión

### Backend

- Node.js + Express, **arquitectura hexagonal + Shared Kernel** (patrones extraídos de `odata-server` y `node-modular-monolith-skill` de referencia).
- Logging: **Pino** (estructurado, por niveles).
- Configuración: **dotenv + zod** (validación por entorno).
- Error handling unificado: AppError + códigos + mapeo HTTP.
- Health checks / readiness en el servidor local.

### Frontend

- **SAPUI5** (MVC, Component.js, routing).
- Build: **UI5 CLI v4** (sucesor oficial de UI5 Tooling, estable, ESM).
- Catálogo de componentes propio (UI Component Playground) + regresión visual con Playwright.

### Persistencia

- **SQLite** como base local (Desktop), arquitectura preparada para múltiples proveedores.
- Migraciones: **Drizzle + Drizzle Kit**.
- **SQLCipher** para cifrado en reposo; claves en el almacén seguro del SO (DPAPI/Credential Manager, Keychain, Secret Service).

### IA / LLM

- **AI Provider desacoplado** (puerto hexagonal: `chat`, `embed`, `listModels`, `pullModel`, etc.), configurable para cualquier proveedor local o remoto.
- Runtime por defecto embebido (llama.cpp/llamafile); adaptadores para Ollama, LM Studio, OpenAI y otros. Pruebas iniciales con LM Studio.
- Gestor propio de modelos (descarga, importación, versionado, cuantizaciones recomendadas por hardware).
- RAG con embeddings dedicados, chunking con solapamiento y actualización incremental.
- Prompts como plantillas versionadas con golden dataset para evaluación.
- Estrategia offline-first: BD local como fuente de verdad, sync incremental con resolución de conflictos configurable.

### Desktop (Electron)

- **vite-plugin-electron** para desarrollo (HMR) + **electron-builder** para distribución.
- Electron solo como contenedor; el Core no depende de Electron.

### Observabilidad

- **OTel SDK + Pino**, export OTLP opcional y deshabilitado por defecto (privacidad-first).
- Loki/Tempo o SaaS (Sentry/Datadog/New Relic) descartados por ahora: sin destino de despliegue y envío de datos a terceros.

## Alternativas evaluadas

| Ámbito         | Alternativas                                            | Resultado                                             |
| -------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| Migraciones BD | Kysely, Prisma, Raw SQL                                 | **Drizzle + Drizzle Kit**                             |
| Build SAPUI5   | Middleware Vite comunitario, Custom Vite + @ui5/builder | **UI5 CLI v4**                                        |
| Build Electron | electron-forge, electron-builder directo                | **vite-plugin-electron + electron-builder**           |
| LLM runtime    | Ollama, Transformers.js, llamafile                      | **Desacoplado: embebido por defecto + multi-adapter** |
| Observabilidad | OTel + Loki + Tempo, SaaS                               | **OTel SDK + Pino, export opcional**                  |
| Versionado     | Calendar, Custom                                        | **SemVer 2.0**                                        |

## Consecuencias

**Positivas**

- Core 100% reutilizable para la futura versión Web (ninguna dependencia de Electron en el Core).
- IA intercambiable sin tocar lógica de negocio (AI Provider Port).
- Privacidad por diseño: datos locales cifrados, telemetría off por defecto.
- Estándares oficiales y estables (UI5 CLI v4, Drizzle, electron-builder).

**Negativas / pendientes**

- El runtime embebido (llama.cpp/llamafile) añade binarios nativos a distribuir; se validará en un spike temprano.
- La reutilización Electron ↔ Web aún no está validada con código real (spike pendiente en Fase 1).
- UI5 CLI v5 en desarrollo: revisar migración futura sin romper el build.
- El testing de IA (determinismo, evals) se materializará con el golden dataset definido en §3.7.
